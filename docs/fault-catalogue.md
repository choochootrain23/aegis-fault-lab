# Proposed fault catalogue

Status: F1 to F16 are implemented and validated on real Docker (see [validation](VALIDATION.md)). No fault is enabled before its isolation and reset checks pass. F6 to F16 come from the [scenario roadmap](scenario-roadmap.md), which also lists the faults still planned.

## Implementation notes (20 October 2026)

- **F1 stopped service** is implemented as specified, on either service. Starting or stopping a container already in that state now reports *unchanged* (Docker's own 304 answer) instead of an unconfirmed result.
- **F4 CPU starvation (new)** was first designed as the broker lowering the target's CPU limit. Measured on the lab, even Docker's minimum limit (0.01 CPU) did not slow these light requests, so it would have taught nothing. The implemented fault starts a bounded runaway background job (three threads, self-stopping after 25 minutes) inside the target's own process, still capped by its 0.25-CPU limit. Measured effect on the catalogue: median latency 390–600 ms against a 5–15 ms baseline, gateway liveness unchanged at ~8 ms. Evidence: slow probes (above 300 ms), Docker stats showing CPU at the container limit with kernel throttling, and a log entry recording the job start. Remedy: stop the job. The broker gained only a read-only `resources` operation; the earlier throttle/restore idea was dropped, so no new mutation privilege was added.
- **F3 disk full** uses each service's existing 8 MiB `/tmp` tmpfs rather than a new 32 MiB data mount. Every business request writes a new small receipt file (rotating at 40), so a full filesystem fails real writes with `ENOSPC`, surfaced as HTTP 507; reads and liveness keep working. The fill routine refuses any scratch space larger than 64 MiB and never writes more than 16 MiB. Remedy: delete only the known filler file. Restarting the container also empties the tmpfs.
- **F5 config drift (new)** overrides one runtime setting in memory, as a bad hot reload would. On the gateway the upstream address moves to port 8080, where nothing listens, so business requests fail with a connection error: from the gateway alone this is indistinguishable from a stopped catalogue, and the lesson is to check the catalogue directly (healthy) and compare the gateway's running config with its deployed values. On the catalogue the data source moves to a dataset that was never deployed, so business requests fail with HTTP 500 and the gateway's fail with them. Liveness, container state, CPU and disk all stay normal. Evidence: the **Running config** check lists each setting beside its deployed value, the **Request trace** shows which step fails, and the log records the reload. Remedy: restore the deployed config. Restarting the container also reloads it, since the override lives only in memory.
- **F2 network delay** is implemented with a deliberate change from the specification below: the delay is **600 ms**, not 1,500 ms. At 1.5 s a delayed service's own probes (and any request needing a fresh connection, which pays the delay twice) would cross the controller's 3-second timeout and look stopped; at 600 ms the lesson stays "slow, not down". Measured over 68 delay rounds and about 4,400 checks, no request failed, because each individual wait stays under the gateways' 1-second upstream timeout: a delayed catalogue's checks took a median of 606–608 ms and both gateways' requests 612 ms, while a delayed gateway paid the delay twice (its call to the catalogue and its reply), so its requests took 1,210 ms with liveness at 607 ms. Fewer than 0.5% of checks paid an extra 600 ms. The broker starts a short-lived helper container with only `NET_ADMIN`, no mounts, a read-only root, no-new-privileges and tight limits in the target's network namespace (`container:<id>`); the helper runs one fixed `tc qdisc` command and is removed. Before adding, it requires the default `noqueue` root; before removing, it requires exactly the fault's netem settings, so it never replaces or deletes a queue it did not create. Measured on the lab: TCP connect to a delayed catalogue ~602 ms against ~1.5 ms, catalogue handler time under 1 ms with ~603 ms outside it, CPU under 1%. Evidence: the **Network path** check (three timed TCP connections plus the service's own `tc qdisc show`), request traces and slow probes with normal CPU. Remedy: remove the delay; a container restart also clears it.
- **F6 packet loss (new, 22 October 2026)** reuses F2's helper with a fixed `netem loss 50%` on the target's egress. Real links already hurt at 1–2%; the lab exaggerates so the effect shows within a minute, and so that a wrong fix cannot pass verification by luck. TCP resends every lost packet after at least 200 ms, so requests are sometimes instant, sometimes about 200 or 600 ms late, and sometimes time out. Because the effect comes and goes, detection counts three failing cycles in the last five, and once failures have come and gone twice the session needs ten consecutive healthy cycles instead of three. **Network path** reports the loss setting and how many TCP segments the service resent since the previous check (from its own `/proc/net/snmp`); a connection attempt that outlasts its 3-second limit is recorded as a measurement rather than failing the check. Removing one network fault's queue leaves the other's alone and reports *unchanged*. Remedy: **Remove packet loss**.
- **F7 quota set to zero (new, 22 October 2026)**, inspired by the public reports of the December 2020 Google authentication outage, where a quota system reduced capacity to zero. The catalogue enforces a per-caller request quota (300 per second for each gateway, room for the retry storm's user traffic, which identifies itself in a header); the quota comes from a separate quota system, not the service's config. The fault pushes 0 for both gateways. The controller's probes have no quota, so the catalogue stays green to its own checks while every gateway request is refused with HTTP 429: monitoring green, users failing. **Running config** is unchanged, so *Restore config* reports nothing changed; the new **Traffic & quotas** check shows per-caller requests, rejections and the quota table. Only the catalogue has quotas, so this fault always targets it. Remedy: **Reset client quotas**.
- **F8 bad release (new, 22 October 2026).** A rollout replaces the stable v1.4.2 build with v1.5.0, whose new price-conversion path fails about half of business requests with a `TypeError` (HTTP 500; 47% measured). The machine, the running config and the network are untouched, so restoring config reports nothing changed. The new **Release history** check shows the running version and every deploy to this process. Remedy: **Roll back release**.
- **F9 memory leak (new, 22 October 2026).** A rollout of v1.5.1 starts a cache warmer that keeps everything it loads, about 12 MiB a second. The service works normally until the container's 192 MiB limit, where the kernel kills it (`OOMKilled`, exit code 137). While the rollout lasts, the controller acts as its **deploy controller**: it restarts a crashed service after three missed health cycles (6 s) and re-applies the release to the fresh process, as Kubernetes would, so the service crash-loops (measured: about 14 s up, 6 s down). Starting it by hand only begins the next loop. The new **Memory** check combines Docker's record of the last exit with the service's own cgroup memory samples and growth rate. Remedy: **Roll back release**, which ends the rollout and starts a crashed service on the stable build. The leak never holds more than 512 MiB in any case, and the out-of-memory kill is confined to the container's own cgroup.
- **F10 traffic flood (new, 22 October 2026).** A separate `reports` service, hardened like the others and on the internal network only, runs a report export job that pulls the catalogue over 256 keep-alive connections. It needs only a few per cent of a CPU to hold the catalogue's 0.25 CPU at its limit (measured on 23 October: about 480 requests a second; the catalogue's checks at about 575 ms and the gateways' at about 500 ms, no failures; first sized at 160 connections, which the cheaper request handling later brought just under the 300 ms slow threshold). There is no job inside the catalogue, so *Stop runaway job* reports nothing changed; the traffic check names report-exporter. Remedy: **Rate-limit top client**, which limits every heavy caller without a deployed quota to 2 requests a second and answers it with HTTP 429 and `Retry-After: 10`. The exporter honours it with a random extra wait: without that jitter, all the connections woke together every 10 seconds and a third of cycles stayed slow, a thundering herd measured on the real lab. Reset stops the exporter and removes the limit. The job stops itself after 25 minutes and only ever calls the catalogue.
- **F11 retry storm (new, 22 October 2026).** The `reports` service runs app users, 60 a second through the target gateway, whose app retries a failed request at once up to three times; six seconds in, it asks the catalogue for an 8-second index compaction that takes its whole CPU and then stops by itself. The timeouts become retries, the retries overload the gateway (four attempts per user against a gateway normally at about 40% of capacity), and the overload outlives the compaction: a metastable failure, localised to a different service from its trigger. The other gateway recovers when the compaction ends. Gateways now count each caller's retries from the `X-Aegis-Attempt` header. Remedy: **Enable load shedding**, which caps a gateway's business requests in flight at 12 and turns the rest away at once with 503; it only takes effect on a gateway that has queued more than that in the last 30 seconds, so elsewhere it reports nothing changed. Stopping a job (the compaction is over) and rate-limiting a client (no unknown caller) change nothing. Reset stops the users and turns shedding off. Measured: sustained for over 70 seconds with the gateway at its CPU limit and the catalogue at 3%; shedding recovered it within about 10 seconds.
- **F12 rack power loss (new, 23 October 2026).** A simulated facility layer models two racks: PDU-A feeds the catalogue and gateway-a in rack R1, PDU-B feeds gateway-c in rack R2. The fault trips PDU-A's breaker; the broker really stops both containers, as cutting power would. While the breaker is open, *Start service* on either reports no power and changes nothing. The new **Facility** check shows the breaker, rack, load, inlet temperature and every service sharing the feed, and every record says `simulated`. The lesson is failure domains: two services failing at the same moment often share something physical. Remedy: **Reset breaker**, which closes it and starts the rack's services, the catalogue first. Reset closes the breaker before starting anything. Inspired by public reports of rack and zone power events, such as the 2015 lightning strikes at St. Ghislain.
- **F13 thermal throttling (new, 23 October 2026).** Inspired by public reports of the 2022 europe-west2 cooling failure. A simulated cooling unit fails; the controller caps every container's CPU at exactly 0.05 through a new fixed broker operation, and the reports service sends steady daytime users, 32 a second through each gateway. Measured: a cap alone barely slows these light requests, so the load is what makes it bite. Under it, the gateways (most work per request) were slow even to liveness, with a median of 308 ms, and failed most business requests, while the catalogue stayed fast. **Lift power cap** is refused while the simulated room is hot and works once cooling recovers, 75 seconds after the failure; reset lifts it regardless. The broker operation sets only 0.05 or 0.25 and passes the same identity checks as every other operation.
- **F14 DNS failure (new, 23 October 2026).** Each gateway now resolves the catalogue itself, as a stub resolver does: a real DNS query over UDP to the nameserver in its `resolv.conf` (Docker's embedded resolver, 127.0.0.11), each answer cached for at most 5 seconds and shared by every request waiting on it. The fault, delivered through the token-protected maintenance endpoint, points the resolver at 127.0.0.53, systemd-resolved's stub address on an ordinary Linux host: an easy setting to copy from a host image, where nothing listens inside a container, so queries are refused. The gateway keeps working until its cached answer expires, then fails every business request with a `NameResolutionError`. Measured on the real lab: a stopped catalogue also fails to resolve (Docker answers SERVFAIL once a container stops), so the **Network path** check tells the two apart. It shows the resolver beside the one deployed, and a TCP connection to the last address that resolved: it succeeds for the DNS fault and times out for a stopped catalogue. Look-alikes: a stopped catalogue (it is up), config drift (the config is unchanged). Remedy: **Restore resolver**; restarting the gateway also restores it. The catalogue resolves nothing, so the fault targets a gateway.
- **F15 brownout (new, 23 October 2026).** The facility layer gains power feeds: each PDU has feed A (active) and a redundant feed B. The fault sags feed A to PDU-B to 186 V, below the 200 V the power supply tolerates. While it lasts, the controller acts as the power: it stops gateway-c through the broker's ordinary stop after five health cycles up, and starts it again after three down, so the service crash-loops with no software cause. Memory stays flat, there is no out-of-memory kill and the release is unchanged, which separates it from F9; the breaker is closed, which separates it from F12. **Facility** shows both feeds, the PSU minimum and a dropout event at each restart. *Start service* works only until the next dip, and because failures come and go, recovery needs ten healthy cycles. Remedy: **Move to redundant feed**, which switches the rack to feed B and starts the service if it is down; reset does the same first. No new broker operation was needed. A container has no power supply, so it stops cleanly (exit code 0) where a real server would simply lose power.
- **F16 partial partition (new, 24 October 2026).** One gateway loses its path to the catalogue while everything else stays healthy, as a bad firewall or routing change would cause. The broker's short-lived network helper (the same NET_ADMIN-only container as F2 and F6) runs a new fixed rule in the gateway's network namespace: a `prio` root queue and one `u32` filter that drops every packet to the catalogue's IPv4 address. The broker reads that address from Docker's record of the owned, validated catalogue container on the fleet network, never from the caller, and refuses an address outside private ranges. Adding needs the default `noqueue` root, so a partition never replaces or coexists with a netem fault; removing deletes the root only when it is exactly that rule (a `prio` root whose only filter drops one destination), and is an honest no-op anywhere else, including the catalogue. Measured effect expected: the gateway's connection setup is never answered, so every business request fails with `ConnectTimeout` after 1 second, while its DNS lookup still succeeds. **Network path** on the gateway reads its own filters with `tc filter show` (read-only) and makes a TCP connection to the catalogue's address, which gets no answer. Look-alikes: a stopped catalogue (it is up), packet loss (no netem queue; total loss to one destination), a DNS failure (the name resolves). Remedy: **Restore route**; restarting the gateway also clears it, since a new network namespace starts with the default queue.
- **Overload safety.** Prototyping the storm wedged the lab three ways, each fixed for every fault: Starlette's decorator middleware cancelled handlers on disconnect and leaked pooled connections (now plain ASGI middleware); Docker's 1,024 open files ran out (now 65,536); and services processed thousands of abandoned requests for minutes after the load stopped (now every request carries a deadline that services honour and propagate, and gateways bound their upstream calls with a bulkhead below the client pool, where a timed-out wait had leaked connections).
- **Verification refinement.** Once a failure has come and gone on its own, recovery needs ten consecutive healthy cycles instead of three. The first recovery after a fix does not count as coming and going, so steady faults keep the three-cycle rule, while a crash loop restarted by hand cannot pass on a short healthy run.
- Injection and remedy for F3/F4/F5/F7/F8/F9 go through token-protected maintenance endpoints on the internal fleet network; the token is separate from the broker credential.
- Reset starts every service, then reverses a non-stop fault on its target. Challenge picks the fault type as well as the target, and hides both.

## Common scenario contract

Review decision: the initial catalogue prioritises polish and repeatability, not a permanently fixed scope. Add scenarios only after evaluating their distinct learning value, evidence quality, isolation and reset reliability. Represent diagnosis, verified recovery and assistance as separate outcomes; a successful reset or a lucky recovery is not proof of understanding.

Require a healthy five-cycle baseline, sufficient resource headroom, expected project/container identities and one active scenario maximum. Record scenario intent in a restricted action ledger; the diagnostic evidence store contains observations without injected fault labels. Injection parameters are fixed enums/bounded values, not commands. The initial lease is 15 minutes with a visible timer, resource-checked extension button and continuation prompt at expiry; at expiry offer Continue for 15 minutes or End and reset, with a visible 60-second grace period before automatic reset if unanswered. Browser closure does not stop deadline enforcement, and cleanup must be verified. Broker records partial failures and reconciles them on restart. Focus on deep, polished scenarios rather than simultaneous injected faults.

Recovery means changing the faulted condition. Reset additionally removes scenario artefacts and returns the synthetic fixture/topology to baseline. Verification means three consecutive successful affected service/business checks after recovery; it is never inferred from a successful control API response. After failed reset, block another scenario and retain the evidence. If the broker is unavailable, the future documented manual reset must operate only on the named project and re-run baseline checks. Never clean up unrelated containers or global networks.

## F1 — Shared dependency process unavailable (first milestone)

- **Target/injection:** B (`catalog-b`), or A for a later local-failure comparison. Broker performs a bounded Docker stop on an exact allow-listed container. Configure fleet restart policy so it does not immediately undo this intentional stop. This tests service unavailability, not crash mechanics or boot/systemd repair.
- **Expected effect:** stopping B causes A (and later C) dependency/business failures while their own liveness succeeds. Direct B probes fail; container state records stopped. Distinguish connection refusal/timeout as actually observed, without demanding a fabricated errno.
- **Diagnosis:** B unavailability explains shared downstream impact. Container stopped plus dependency errors supports this; it does not establish an unexpected underlying crash cause. Stopping A instead should leave B and C healthy.
- **Recovery:** start the same expected container after identity validation; inspect failures explicitly.
- **Reset:** start every expected fleet node, confirm fixture presence, clear active lease and verify baseline. Do not erase incident history. A tmpfs fixture may need deterministic reseeding on B startup.
- **Acceptance:** three repeats, evidence appears within 10 seconds, unaffected liveness remains healthy, and verification succeeds within 15 seconds of B readiness.

## F2 — Dependency response delay through isolated network impairment

- **Target/injection:** B's dedicated network namespace. A short-lived helper with only required `NET_ADMIN` attaches to that exact container namespace and applies a fixed 1,500 ms egress delay to its validated interface using netem. A/B HTTP timeout is 1,000 ms. No host interface, default VM route or host namespace may be accepted. No packet-loss randomness initially.
- **Prerequisites:** verify kernel/netem availability and actual namespace identity; helper has no Docker socket or host mounts. If rootless networking or kernel limitations prevent this, defer this scenario. An application sleep may be a separately labelled alternative, never represented as network impairment.
- **Expected effect:** real traffic to/from B experiences delayed responses; A/C dependency timeouts rise, B process remains running, container CPU need not rise, and direct B probes can time out too. A/C liveness remains normal. A bounded diagnostic probe with a longer 3-second timeout may observe B responding slowly; keep this distinct from the normal collector timeout.
- **Diagnosis:** reachable-but-slow dependency path is supported; observations alone may not isolate network delay versus application delay. Report that ambiguity unless independent transport measurements resolve it. Do not expose the injected qdisc configuration as the AI's answer key.
- **Recovery:** fixed removal of the scenario-owned qdisc from the same namespace; do not delete pre-existing unrelated qdiscs. Refuse injection when an unexpected qdisc is present.
- **Reset:** verify scenario qdisc absent and baseline latency restored. If target recreation changed namespace identity, discard stale handles and reconcile the new target; never apply cleanup to a guessed interface.
- **Acceptance:** record latency before/during/after, real timeout evidence, helper lease cleanup and unchanged primary VM connectivity. A local namespace fault has real effects but does not demonstrate physical-switch repair.

## F3 — Bounded writable filesystem full

- **Target/injection:** B's dedicated 32 MiB data tmpfs, containing only regenerable synthetic fixture data and scenario files. A fixed routine creates a filler file in bounded chunks until a reserved cap or `ENOSPC`; permit enough room for initial fixture, then exhaust only this mount. Read-only root filesystem and memory cap remain enforced. Never fill a host bind mount, Docker overlay, controller database or `/`.
- **Expected effect:** B liveness and existing reads can remain healthy while a synthetic receipt-write request fails with recorded `ENOSPC`; free bytes on the scoped mount approach zero. Gateway business path must include this write for the scenario so its failure is real and observable. Compare healthy read path with failing write path to avoid diagnosing total service outage.
- **Diagnosis:** the scoped filesystem is full and writes fail. This is real filesystem-capacity troubleshooting, not physical disk failure, SMART data, storage latency or block-device I/O degradation.
- **Recovery:** remove only the known filler file, then issue a fresh bounded synthetic write/readback and verify gateway business requests.
- **Reset:** remove scenario receipts/filler from the dedicated mount, reseed the fixture if needed, verify expected mount size/free capacity and baseline. Restarting B clears tmpfs, so record that reset mechanism if used rather than claiming file deletion succeeded.
- **Acceptance:** repeat three times without OOM, show actual write error and scoped usage, demonstrate successful write/readback after reset, and show no growth beyond bounded logs/state on the VM filesystem. If memory enforcement or mount identity cannot be verified, disable this scenario.

## Deferred storage I/O extension

True block-device I/O throttling/contention is deliberately deferred: it introduces storage-driver and device-accounting assumptions and could contend with unrelated VM work. No `fio` against host devices, loopback filesystem setup or host disk-pressure workload is proposed now. F3 satisfies the storage-impairment objective with a safer, bounded real failure. A later extension needs its own resource isolation argument and measurable distinction between application delay and actual I/O latency.

## Cross-scenario evidence checklist

Capture baseline, affected node/generation, liveness/readiness/business outcomes, timestamps, relevant logs, scoped metrics, diagnosis with alternatives, human recovery action, post-recovery checks and reset outcome. Retain failures and truncation markers. The separate action ledger supports evaluator ground truth and auditing; it cannot replace diagnostic evidence. Compare F1-on-B with F1-on-A to demonstrate shared versus local effects before adding more fault types.
